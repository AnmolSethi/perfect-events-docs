Post-Install Security Checklist

What the platform already handles for you, and the handful of things only you can set.

Most of the hardening below ships on by default — nothing to configure. This page is mainly about the few things that depend on your environment.

Already handled for you

  • Security headers on every response — Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, and Strict-Transport-Security whenever the request is HTTPS.
  • Rich-text sanitization — CMS page bodies and FAQ answers are sanitized on save; an admin account being compromised (or a copy-pasted body with embedded script) can't turn into stored XSS.
  • Upload type restrictions — logo, favicon, organizer logo, and event cover/gallery uploads are restricted to JPEG/PNG/GIF/WebP; SVG is deliberately excluded everywhere uploads are accepted, since an SVG can carry a script.
  • Rate limiting — public search/discovery endpoints and the whole API have floor-level throttles against scraping and brute-force abuse.
  • Signed, verified webhooks — every payment gateway's webhook is signature- and amount-checked before it's trusted; a webhook URL alone is never enough to fake a payment.
  • Signed QR tickets — ticket QR codes are HMAC-signed; the scanner rejects a forged or altered code even if someone guesses a ticket's code format.
  • Email verification gates checkout for self-registered accounts.

Things you need to set yourself

  • Use HTTPS. Enable AutoSSL/Let's Encrypt and set APP_URL to https:// — the app automatically enables secure session cookies and HSTS once it sees that. Running over plain HTTP after launch is the single biggest gap on this list. See HTTPS.
  • Use a strong admin password. The install wizard enforces a 10-character minimum on the admin account it creates, but a long, unique password (ideally from a password manager) is on you.
  • Keep gateway credentials to live keys only in production. Double-check each payment gateway is switched from its test/sandbox mode to live mode (Admin → Settings → Payment gateways) before you actually launch — see Integrations for each gateway's specific keys.
  • Turn on SMTP for real mail delivery. If you left the Mail step on the `log` driver during install, transactional emails (password resets, ticket receipts, verification links) are only being written to a log file, not delivered. Set real SMTP from Admin → Settings → Mail.
  • Restrict database credentials. Use a MySQL user scoped to only the PerfectEvents database, not a shared root-equivalent account.
  • Keep automated backups. There's no built-in backup feature yet (see Backups) — set up your host's or provider's own scheduled MySQL dump + file backup for storage/app/public (uploaded media) if you don't already have one.
A known, deliberate trade-off The default Content-Security-Policy allows unsafe-eval/unsafe-inline in script-src because the Admin/Organizer panels use Alpine.js (via Livewire), which evaluates inline expressions. The policy still meaningfully restricts framing, object embeds, and form submission targets — it isn't a no-op — but it isn't a maximally strict CSP either. This is an intentional limit of the hand-rolled-panel architecture, not an oversight.
