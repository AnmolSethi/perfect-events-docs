API Overview

How the mobile apps (or your own client) authenticate against /api/v1.

Everything under /api/v1 is the same API the Flutter apps use — there's no separate "public API" with reduced functionality. A token-holding client can do anything the account type it belongs to is allowed to do.

Authentication

Token-based via Laravel Sanctum. Two ways to get a token:

RouteNotes
POST /api/v1/auth/loginEmail + password + a required device_name. Returns a bearer token.
POST /api/v1/auth/registerSelf-registration — customer accounts only. Organizers apply through the website; staff accounts are created by their organizer.

Both are rate-limited against brute force. Send the token on every subsequent request:

Authorization: Bearer {token}

Tokens don't auto-expire. POST /api/v1/auth/logout revokes just the current token (other devices/sessions stay logged in).

Abilities — what a token can do

Coarse, per account type, checked at the middleware layer (not just in application logic — a staff token literally cannot reach a route outside its ability):

Account typeAbilities
Admin* — everything
Organizer* — everything (scoped to their own data by policy checks, not by ability)
Stafftickets.scan only
Customertickets.view only

This is a separate, coarser mechanism from the roles/permissions system described in the permissions matrix — abilities gate which API routes a token can reach at all; roles/permissions further gate what an authenticated user can do once there.

Key route groups

GroupNotes
Discovery — events, categories, pages, organizersFully public, no auth, IP rate-limited.
CheckoutAuth required — no guest checkout, by design.
Scanner (/api/v1/scanner/*)Requires the tickets.scan ability — a staff token can reach these and nothing outside them.
Payment webhooks (/api/v1/webhooks/{gateway})Public/unauthenticated — trust comes from each gateway's own signature verification, not a token.
Profile, tickets, orders, notificationsThe authenticated user's own data.

Response shape

Successful responses wrap their payload in a consistent envelope ({"data": ...}); paginated list endpoints include a meta.pagination block. Errors return a consistent shape with an HTTP status and a machine-readable error code (for example EMAIL_NOT_VERIFIED when checkout is blocked pending email verification) rather than just a human-readable message.

What's deliberately not here yet No refresh-token rotation, no 2FA-over-API challenge, and abilities don't go any finer-grained than the four rows above. These are known, deferred scope — not gaps to work around.
