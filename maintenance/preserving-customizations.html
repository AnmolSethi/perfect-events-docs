Documentation / Maintenance

Preserving Customizations

There's no plugin system — keep customizations in version control, and prefer the safe extension points where you can.

PerfectEvents doesn't have a formal plugin/hook/override-file system. If you edit application code directly, an update that touches the same file will overwrite your change — there's no automatic merge. This page is about minimizing that pain, not eliminating it entirely.

The practical strategy: version control

Put your install under git from day one (a private repo, not the CodeCanyon zip's own history). Commit before every update. When a new release lands:

  1. Commit or stash your current state.
  2. Apply the new release's files as a new commit (or a merge, if you're comfortable with git — this is exactly what a merge is good at: reconciling your changes against upstream changes to the same files).
  3. Resolve any conflicts — git will tell you exactly which files both you and the update touched, rather than silently discarding either side.

This turns "did I lose my customization?" from a manual diff-everything exercise into git doing what it's built for.

Prefer settings and content over code, where you can

Anything already covered by Admin vs. rebuild — branding, CMS pages, notification copy, homepage layout, translations — survives every update automatically, because it lives in the database, not in a file an update replaces. Before editing code for something, check the settings reference — it may already be a setting.

Where the codebase is actually built to be extended

A few areas use a driver/registry pattern specifically so a genuinely new capability doesn't require touching existing files, which makes it much easier to carry forward across updates:

  • Payment gateways — adding a new one is one new class implementing PaymentGateway plus one config entry; CheckoutService and the rest of checkout never need to change.
  • Homepage sections — new section types are registered the same way, by key, rather than hardcoded into the homepage view.

A new file you add yourself (a new gateway class, for example) is untouched by an update almost by definition — it's changes to shipped files that are at risk.

Be extra careful editing shipped files that carry business logic A styling tweak to a Blade view is low-risk to redo after an update. A change inside CheckoutService, a payment gateway driver, or anything money/ticket/auth-related is higher-stakes to lose track of — this is exactly the kind of change version control is worth having before you make it.
