Documentation / Mobile Apps

Project Structure

Two standalone Flutter apps — open either folder and run it like any Flutter project.

flutter/
└─ apps/
   ├─ customer/     ← discovery, checkout, ticket wallet, orders, profile (V1, in this release)
   │  ├─ lib/core/  ← API client, auth/token storage, design tokens, shared UI, formatting
   │  ├─ lib/src/   ← the app's features
   │  ├─ assets/    ← fonts + default branding
   │  ├─ config/    ← dev.json (you create this), prod.json.example
   │  └─ tool/rebrand/ ← the rebranding kit — see Rebranding the apps
   └─ scanner/      ← staff auth, event select, QR scan + check-in, scan history (V1, in this release)
      └─ (same layout)

Why two separate apps, not one

Customers and door staff have different users, different permissions, different navigation, and different release cadences — a customer downloading your ticketing app has no reason to also download door-staff scanning tools. Each app is a complete, self-contained Flutter project with its own pubspec.yaml, android/, ios/, store listing, icon and config. Building or shipping one never touches the other.

Opening an app

Open flutter/apps/customer (or flutter/apps/scanner) in Android Studio or VS Code, then run flutter pub get. No monorepo tool, no shared package to set up. Both apps contain the same lib/core/ code; if you change something there and want it in both apps, make the change in each.

Per-app commands

Run these from inside the app's directory (e.g. flutter/apps/customer):

fvm flutter run --dart-define-from-file=config/dev.json
fvm flutter build appbundle --dart-define-from-file=config/prod.json   # Android
fvm flutter build ipa       --dart-define-from-file=config/prod.json   # iOS, Mac required

See Building Android and Building iOS for the full release process.
