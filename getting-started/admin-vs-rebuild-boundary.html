Admin vs. Rebuild

What you can change from a panel, and what needs a code change — read this before you start customizing.

Every setting in this product falls into one of two buckets. Knowing which bucket something is in before you start saves you from either editing code unnecessarily, or hunting for a setting that was never going to exist as a toggle.

AdminRebuild
Where it livesAdmin → Settings, saved to the database, takes effect immediatelySource code / Flutter config files, needs a redeploy or app rebuild
Who can change itAny super-admin, anytime, no developer neededWhoever manages your codebase
ExamplesSite name, logo, brand color, currencies, languages, payment gateway keys, commission rate, coupon rules, notification templates, CMS pages, homepage layout blocksMobile app icon/splash/package id, adding a new payment gateway, changing the checkout flow itself, custom report types

Why the split is where it is

The rule of thumb: if it's a value (text, a color, a key, a limit, which gateways are on), it's a setting. If it's behavior (a new step in checkout, a new kind of ticket rule, a new integration this product doesn't already support), it's code. The web side (site name/logo/colors/currencies/languages) is fully Admin-driven — see Admin tour and the full settings reference.

The one place this gets more involved: mobile apps

The Flutter apps pull brand color, name, and logo from the server at runtime — same as the website. But an app's icon, splash screen, package id, and store listing are baked into the compiled binary; those require a rebuild. See Mobile Apps → Admin-configurable vs. rebuild for the exact list of which mobile values are which.

Rule of thumb If you're not sure which bucket something falls in, check the settings reference first — if it's not listed there, it's a code change.
